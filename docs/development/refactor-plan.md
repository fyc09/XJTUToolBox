# XJTUToolBox 重构 PLAN

状态：实施中。本文保存已确认的架构约束与完整迁移计划。首批实现、验收结果与剩余范围见 [重构实施记录](./refactor.md)。

## 1. 重构目标与范围

保留 Python 业务实现，GUI 迁移到 Qt6：采用 PySide6、Qt Quick/QML 和官方 Qt Quick Controls，固定使用 Basic Style，外观只提供深色与浅色两种模式。退出现有 GUI 组件体系，重用已验证的校园系统访问、解析和认证能力。将业务按接口层、服务层、GUI 层、CLI 层划分，使 GUI 与 CLI 使用同一套服务流程，并统一任务执行、进度、取消、账户上下文和错误传播。

本次不迁移 Electron 或 JavaScript/TypeScript 业务栈。QML 中的 JavaScript 只用于展示绑定和轻量交互，不承载业务流程。GUI 按功能与分层重构一同迁移，不同时重写 HTTP 库和数据库。第一阶段继续兼容同步接口，通过统一执行适配器让阻塞操作离开 GUI 主线程。异步化留到边界稳定以后独立评估，不能成为分层重构的前置条件。

这里的“接口层”指校园系统、认证、存储等功能接口，不指 Qt 中名称带 Interface 的界面类。

本文中的“必须”“禁止”是新增及迁移代码的硬性规则。现有遗留代码按迁移清单逐项退出，不要求第一步全量符合，但禁止扩大遗留模式。

## 2. 四层职责

| 层 | 职责 | 对外提供 | 不承担的职责 |
| --- | --- | --- | --- |
| 接口层 `api/` | 封装外部系统协议、单项功能、数据解析及底层存储操作 | 有明确输入、返回值和错误的功能调用；必要时返回数据流、分页数据或操作状态 | 用户操作的完整流程、进度上报、任务调度、界面、终端交互 |
| 服务层 `services/` | 将接口功能编排为用户可以执行的完整流程；定义业务规则、阶段、缓存策略、重试政策和结果 | GUI/CLI 共用的公开服务入口；输入/结果契约；通过统一上下文上报进度 | Qt/QML 对象操作、终端输出、具体线程管理、直接 HTTP/SQL 调用 |
| GUI 层 `gui/` | 输入收集、展示、交互、页面状态、结果与进度呈现 | QML 页面、官方控件、Python 展示模型和 GUI 执行适配器 | 校园系统协议、业务流程、数据库操作、账户凭据管理 |
| CLI 层 `cli/` | 命令参数解析、输入收集、输出格式、进度展示、退出码和终端取消 | 可独立运行的命令入口 | Qt 依赖、校园系统协议、独立重写的业务流程、数据库操作 |

强制调用方向：GUI/CLI → 服务层 → 接口层。GUI 和 CLI 是并列入口，二者不得互相依赖。

服务层提供的是“查询成绩”“同步课表并导出”“下载 LMS 文件”“批量执行评教”等完整操作。GUI/CLI 不能自己拼接“登录 → 请求 → 解析 → 缓存 → 导出”。

接口层的“单项功能”不等于“只能发一次 HTTP 请求”。一个登录协议或一次分页请求可能需要若干底层步骤；这些属于接口内部的协议实现。接口层不得因此承担整项用户流程或引入进度接口。

## 3. 依赖与 import 硬性规定

以下约束针对直接依赖，包含正常 import、动态 import、类型检查专用 import，以及通过工具模块绕过分层的调用。GUI 调用服务后由服务间接使用接口，是允许的正常依赖链。

| 所在位置 | 允许直接依赖 | 明确禁止 |
| --- | --- | --- |
| `api/` | 基础数据/错误契约、底层 HTTP/认证/存储设施、必要的协议解析库 | `services`、`gui`、`cli`、任务运行模块、任何 Progress/TaskContext 契约；`PyQt*`、`PySide*`、`qfluentwidgets`；`rich`、`click`、`typer` 等终端展示/命令框架 |
| `services/` | `api` 的公开入口、基础数据/错误契约、服务输入/结果契约、进度/取消协议、纯业务辅助函数 | `gui`、`cli`、具体任务执行器；`PyQt*`、`PySide*`、`qfluentwidgets`；`requests`、`httpx` 等 HTTP 实现；`peewee`、`sqlite3` 等存储实现；终端展示/命令框架 |
| `gui/` | 服务层公开入口、公开契约、PySide6/官方 Qt Quick 模块、与 GUI 有关的执行适配器 | `api`、底层 HTTP/会话/认证/数据库模块、接口层内部实现、CLI 模块；`PyQt*`、PySide2、`PySide6.QtWidgets`、`qfluentwidgets` 及其他第三方 UI 库；直接使用凭据存储或全局账户对象执行业务 |
| `cli/` | 服务层公开入口、公开契约、与 CLI 有关的执行适配器、参数解析/终端展示库 | `api`、底层 HTTP/会话/认证/数据库模块、接口层内部实现、GUI 模块；所有 Qt/UI 库 |

附加规则：

1. 不得在接口层或服务层创建 Qt/QML 对象、弹窗、InfoBar、进度条，或输出面向用户的终端文本。
2. 不得在服务层创建/继承 QThread、QRunnable、QObject，定义 Qt signal，或调用线程池、进程池、事件循环启动任务。
3. 不得在 GUI/CLI 中调用原始 HTTP、SQL、ORM 模型、学校网页解析函数，或直接操作认证 Cookie。
4. 不得把违规依赖放进 `utils/`、`common/` 等目录，再从各层导入。工具模块必须归属明确的一层或有明确的基础职责，并服从同样的依赖规则。
5. 不得以类型注解、回调或返回值跨层传递 Qt/QML 对象、Qt signal、HTTP Response、ORM 实体、会话客户端或数据库连接。
6. GUI/CLI 只能调用服务公开入口；禁止导入服务内部 helper 来拼装业务流程。服务同样只能依赖接口公开入口。
7. 服务与接口允许使用结构化日志。日志不是进度接口，也不能用来驱动 GUI/CLI 状态。

## 4. 公共契约与基础设施

四层之外允许存在少量支撑模块，它们不是新的业务层，也不得成为任意跨层调用的入口。

| 支撑模块 | 允许的内容 | 边界 |
| --- | --- | --- |
| `contracts/` | 基础数据类型、错误类型、服务输入/结果、进度/取消协议 | 不 import 四个业务层、Qt、HTTP/ORM 实现；基础数据与任务契约分开，接口层只用基础部分 |
| `infrastructure/` | HTTP 客户端、账户会话管理、凭据存储、数据库/文件适配等实现 | 不包含完整用户流程，不依赖 GUI/CLI；通过接口层暴露功能，前端不得直接调用 |
| `runtime/` | 与 Qt 无关的任务记录、生命周期、取消令牌、进度事件协调 | 不包含校园业务，不依赖 GUI/CLI；执行具体线程或事件循环的方式由入口适配器提供 |
| 启动装配模块 | 创建依赖并将服务/执行适配器注入入口 | 是有限的装配位置，不处理业务、不提供运行时服务定位器 |

Qt 相关执行桥接代码归 GUI 适配器，不能混入 `runtime/` 或服务层。CLI 必须能在不安装、不初始化 Qt 的情况下导入并使用服务。

不要求每个函数都有接口类、工厂或依赖注入框架。只在需要替换、测试或隔离底层实现的边界使用明确契约；禁止为分层而新增没有职责的转发层。

## 5. 接口层规则：只提供功能，不提供 progress

### 5.1 功能与数据

- 每个公开功能必须声明输入、返回数据、可能错误和副作用。
- 认证、查询、提交、下载、解析、读取缓存、写入缓存等能力必须有明确归属，不能从 UI 借用 helper。
- 解析/规范化属于接口层；“这些数据对本次用户操作意味着什么”属于服务层。接口层可以校验协议结构，服务层决定业务处理。
- 返回稳定的数据对象，不暴露 HTTP Response、HTML 解析树、ORM 模型或底层连接。错误也要转换成基础契约中的错误，不把库实现细节作为公开接口。
- 存储接口负责读写与事务执行；服务决定何时使用缓存、缓存归属、何时提交，以及失败时的业务行为。

### 5.2 进度禁令

- 公开签名和内部实现不得接收 Progress、TaskContext、进度回调、Qt signal 或 CLI 进度对象。
- 禁止返回专门用于展示的百分比、阶段文案、任务状态事件。
- 禁止用“通用 callback”“event sink”等名称变相注入进度。
- 分页结果、下载字节块、上传后的真实处理状态等属于功能数据，允许返回。服务层据此计算进度；不得为了 UI 进度制造没有功能含义的数据流。

### 5.3 长操作与细粒度进度

对于下载、分页、分批提交等操作，接口应在真实的功能边界返回数据，例如分块字节流、单页结果或一次提交结果。服务层消费这些数据，检查取消并上报进度。

对于无法拆分的阻塞调用，接口层设置明确的 I/O 超时，服务层展示不确定进度。禁止为了获得进度，把 TaskContext 传到接口层。

流式接口必须有明确的关闭机制。正常结束、消费方取消和异常退出都必须释放资源。不得为了认证判断、日志或错误展示提前读完整个大文件响应。

### 5.4 超时与副作用

- I/O 超时及协议级资源释放属于接口/基础设施，不依赖任务进度或 Qt 定时器。
- 接口不得读取“当前选中的账户”；需要的账户绑定客户端或会话必须显式提供。
- 重试范围须明确：底层只做已定义的安全协议恢复；是否重试整个业务步骤由服务决定。禁止两层隐式嵌套重试。
- 提交、支付、评教等有副作用的操作，不得因普通网络异常自动重复提交；服务需根据明确结果或可验证状态决定后续处理。

## 6. 服务层规则：完整流程与业务进度

### 6.1 服务入口

- 每个用户操作必须有一个明确的公开服务入口，覆盖其完整流程。
- 入口接收显式参数、固定账户标识及统一运行上下文，返回结构化结果或抛出明确错误。
- GUI/CLI 必须复用同一入口，不能各自维护查询、缓存、重试、下载、导出或批量提交逻辑。
- 公共子流程可以复用，但不得形成循环依赖或未经约束的跨服务调用网络。
- 服务不启动自己，线程调度、任务登记及生命周期管理不属于服务。

### 6.2 进度契约

Progress 是服务输出的业务数据，不是线程生命周期。统一协议支持以下信息：

| 字段 | 语义 |
| --- | --- |
| 阶段标识 | 稳定、可识别的业务阶段，例如认证、读取课程、下载、写入缓存 |
| 阶段说明 | 普通文本，描述正在执行的业务动作，不包含 UI 标记或终端控制字符 |
| 已完成量/总量 | 可选；只能在同一阶段、同一单位下比较；总量未知时不填写确定百分比 |
| 单位 | 字节、条目、页、课程等真实工作量 |
| 总体进度 | 可选；仅在存在明确计算方式时提供，范围统一为 0–100 |

- 进度上报调用统一采用同步的“提交事件”语义，不承担 GUI 刷新、不等待用户输入；不得混用有时需要 await、有时不需要 await 的契约。
- 无进度需求的执行场景使用同一协议的空实现，服务不用判断自己运行在 GUI 还是 CLI。
- 阶段与任务状态分开。进度达到 100 不能宣告任务成功；成功只由正常返回确定。
- 总量未知则展示不确定进度。禁止用定时器伪造百分比，禁止把未经定义的阶段编号直接当作总体完成比例。
- 并发子操作的汇总由服务决定；完成量必须一致，不能让多个子任务各自把总体进度写到 100。
- 下载事件的单位、总量及分母口径必须一致；无法确定时只报告已下载量。
- 服务在阶段边界和真实数据推进时上报。展示层/执行适配器可合并高频事件，但必须保留最新数据和终态。

### 6.3 取消、结果与输入

- 服务在步骤间、循环中、写入/提交前检查统一取消令牌；接口层不 import 该令牌。
- 被取消时停止后续步骤，并清理自己持有的流、临时文件和事务；已完成的外部副作用不能假装已撤销。
- 简单查询返回数据；批量流程返回已完成、失败、未执行等可区分结果，不能把部分失败伪装成全部成功。
- 用户取消后的任务记录必须保留已完成副作用的摘要，GUI/CLI 使用同一结果规则展示。
- 验证码、二次确认等用户输入不能在服务中弹窗或调用 input。服务以明确的“需要输入”结果/错误返回挑战数据，由入口收集输入后继续调用服务。
- 输入续接只能携带明确、账户绑定、可失效的数据，不向 GUI/CLI 暴露活的会话或线程对象；禁止借进度事件请求用户输入。

## 7. GUI 层规则

### 7.1 已确定的技术路线与外观范围

- 新 GUI 固定采用 Qt6、PySide6、Qt Quick/QML 和官方 Qt Quick Controls，显式选择 Basic Style，不能依赖操作系统的默认样式选择。
- 不引入第三方 UI/主题库，不使用 Material、FluentWinUI3 等其他样式；新界面不使用 Widgets，也不将旧 Widgets 嵌入 QML。
- 唯一的外观选项是浅色与深色。使用统一的应用级 palette 管理两种模式，控件继承配色；不得逐控件硬编码两套颜色。仅补充明暗模式所需的最小配色，不建立额外主题系统。
- 保留 Basic 的默认控件外观、字体、尺寸和交互反馈。不增加强调色、字体、圆角、密度、主题包等外观设置，不为美化重写控件的背景或内容项。
- 页面仍需完成正常的布局、导航、数据展示和业务状态提示；这些属于功能开发。必要的状态表达使用统一语义，不绕过明暗配色规则。界面效果由维护者审核，不把视觉美化作为本次重构的前置工作。
- 明暗模式选择的持久化通过设置服务完成；palette 的应用与刷新归 GUI。接口与服务不依赖 Qt palette，也不接收 QML 外观对象。

### 7.2 QML 与 Python 展示模型的边界

- QML 只声明界面、属性绑定和轻量交互，通过 GUI 层的 Python 展示模型/控制适配器发起操作；不得直接编排服务流程。
- Python 展示模型归 `gui/`，允许使用 PySide6 的 QObject、属性、signal 和 Qt 数据模型，负责调用服务公开入口及统一执行适配器，并将结果转换为可展示的数据。
- QML 不得使用 XMLHttpRequest 等能力访问校园接口，也不得访问会话、数据库、凭据或文件存储；禁止通过桥接对象绕过四层边界。
- 不向 QML 暴露原始服务实例、TaskContext、底层客户端或 ORM 实体。公开桥接只提供展示数据和有限的交互方法，不能提供任意函数调用或模块访问入口。
- QML 不重复保存一套业务任务状态。运行状态、进度和结果绑定展示模型；本地状态只用于选中项、展开项等纯展示行为。
- GUI 适配器在主线程更新展示模型及其 Qt 属性/模型通知；后台 worker 不直接修改 QObject、QML 对象或 Qt 模型。

### 7.3 任务与页面交互

- 页面只负责用户输入、当前选中账户、展示状态及服务结果。
- 启动任务前将输入与账户标识固定；运行过程中不得通过页面对象或全局 `accounts.current` 重新获得业务账户。
- 所有 Qt 控件访问必须在 GUI 主线程；后台执行只返回数据、错误和进度事件。
- GUI 使用一个统一的执行适配器启动服务，禁止新增“一功能一个 QThread 子类”。业务函数不能嵌在 QRunnable/QThread 的 run 方法中。
- 进度组件绑定任务公开信息，禁止持有并管理业务线程；禁止轮询 isRunning 来推断业务是否成功。
- 页面可以控制显示、隐藏、按钮状态、订阅和取消请求，但不能决定任务终态。
- 页面销毁时必须解除订阅。晚到的结果必须按 task_id 和请求代次核验，不能更新另一个账户或新一轮请求的页面。
- 页面关闭和取消任务是两件事。普通临时查询可按页面政策请求取消；下载等允许继续的任务由统一任务记录持有，不依赖控件寿命。
- 设置、缓存、导出、账户增删等产生业务或持久化副作用的动作也走服务入口；GUI 不得另开持久化后门。
- 错误到展示文本的映射在 GUI 层完成；服务提供可判别错误和必要上下文，不提供 InfoBar 对象或窗口标题。

## 8. CLI 层规则

- 命令只做参数解析、调用服务、展示结果/进度和设置退出码。
- CLI 不创建 QApplication，不 import GUI 页面、Qt 执行桥接或 Qt 数据类型。
- 默认单命令可以直接执行同步服务，不为形式统一强制启动线程池；需要并发时使用 CLI 执行适配器，遵守同样的任务与账户规则。
- Ctrl+C 转换为取消请求，让服务在安全边界停止并释放资源。正常取消路径不使用强杀线程。
- 普通文本、表格、JSON 等输出只转换服务结果，不从接口补查数据。机器可读结果与进度/诊断输出必须使用不同通道，不能让进度文本破坏 JSON。
- CLI 的退出码约定需固定并记录：成功、业务失败、需要输入、取消/中断等不能混成成功退出。
- CLI 不维护另一套登录策略、缓存策略、业务重试或批量操作实现。

## 9. 数据与账户归属规则

1. 当前选中账户是入口状态，不是后台业务依赖。任务必须绑定启动时的 account_id，而不是可变的“当前账户”对象。
2. account_id 必须稳定且不可复用；账户删除后重建不能继承旧任务的权限或缓存归属。
3. 显式传 account_id 只是必要条件。实际会话、缓存、返回结果和写入目标都必须绑定同一账户，禁止底层再次转向全局 current。
4. 会话及凭据由基础设施管理，通过接口层提供能力；GUI/CLI 不持有可供业务使用的会话、Cookie 或数据库实体。
5. 首阶段对同账户的共享会话访问采用明确的串行策略，登录刷新也纳入该策略。禁止在多个任务里无约束地共享和修改同一个会话。以后允许并行时须先证明会话隔离或同步边界。
6. 切换账户不改变已有任务身份。删除账户、注销或凭据失效则必须使该账户上下文失效，并请求取消关联任务；清理敏感资源后旧任务不得重新提交缓存或业务写入。
7. 账户失效与结果/写入提交必须有统一协调点，不能只在任务开始时检查一次。取消请求本身不能保证阻塞调用立刻结束。
8. 跨层结果使用数据快照。前端不能修改服务内部集合、缓存对象或共享配置来改变后台任务行为。
9. 数据库连接、事务和流的创建/关闭归属明确。GUI 不持有 ORM 对象；跨线程不传递活的连接或事务。
10. 服务结果、进度、错误和日志不得携带密码、会话 Cookie 等凭据。需要输入的挑战数据也应只包含入口完成该交互所需内容。

## 10. 统一任务生命周期

任务机制是执行支撑，不是一层业务 Service，也不是 Qt 控件的附属状态。

| 状态 | 定义 | 允许的后续状态 |
| --- | --- | --- |
| PENDING | 已登记，尚未开始执行 | RUNNING、CANCELLED |
| RUNNING | 执行器正在调用服务 | SUCCEEDED、FAILED、CANCELLED |
| SUCCEEDED | 服务正常返回，必要提交与资源收尾已完成 | 无 |
| FAILED | 服务异常结束，错误及收尾已确定 | 无 |
| CANCELLED | 取消已落实，服务已退出并完成资源收尾 | 无 |

PENDING 用于真实排队，避免线程池尚未执行时就宣称 RUNNING。取消请求是令牌上的请求标记，不另造一套 UI 任务状态，也不立即等同于 CANCELLED。

硬性规则：

- 只有统一执行机制写任务状态。服务返回结果、抛出业务异常或取消异常；GUI/CLI 只展示状态并请求取消。
- 每个任务只产生一次终态。晚到进度、重复完成通知、终态后的取消请求不得改写结果。
- 取消与成功竞态由统一机制按已确定的完成/提交规则处理；成功完成后收到取消请求不能把已成功任务改为取消。
- 阻塞调用未返回时，UI 可以显示“正在取消”，但任务仍未进入终态。不能隐藏这个事实或提前释放仍被使用的资源。
- 第一阶段同步阻塞 I/O 的取消是协作式的，受调用超时约束。不得承诺立即停止，禁止使用 QThread.terminate 或等效强杀作为正常流程。
- 每个事件必须能关联 task_id 和账户。线程编号、控件地址、当前页面账户都不能代替任务身份。
- Qt signal 只承担 GUI 通知桥接，不负责拼接业务状态机。普通方法返回、异常与取消收尾决定任务结果。
- 应用退出必须先停止接收新任务、请求取消并执行有边界的资源收尾。遗留 worker 不能因页面销毁而失去管理者。

## 11. 典型功能的归属示例

| 场景 | 接口层提供的功能 | 服务层提供的完整流程 | GUI/CLI 的工作 |
| --- | --- | --- | --- |
| 查询成绩 | 认证功能、查询并解析成绩、缓存读写 | 固定账户 → 确认认证 → 查询/选择缓存策略 → 整理结果 → 返回 | 收集参数、执行、显示成绩和错误 |
| 同步课表并导出 | 查询课表、查询考试、缓存/文件写入功能 | 认证 → 获取数据 → 校验/合并 → 保存/导出 → 返回文件结果 | 选择导出参数、显示阶段和结果 |
| LMS 下载 | 查询文件元数据、打开可关闭的字节流、底层文件操作 | 认证 → 确定下载对象 → 消费数据流/检查取消/报告字节进度 → 校验 → 完成文件提交 | 选择文件/路径、显示下载量、请求取消 |
| 批量评教 | 查询待评项目、提交单项、查询提交状态 | 读取项目 → 逐项提交与核验 → 上报数量 → 记录部分结果/停止后续提交 | 选择参数与确认操作、显示汇总 |

服务提供 GUI 和 CLI 所需的相同功能闭环。界面表格排序、颜色、折叠等纯展示行为仍由入口处理。

## 12. 迁移步骤与验收门槛

按功能纵向迁移，先把一个功能贯通四层，再扩展到其他功能。禁止先建立大量空框架、同时搬动所有模块而长期没有可用功能。

### P0：盘点与边界冻结

- 盘点现有接口、线程、页面、认证、账户、缓存、导出功能及 GUI 线程相关操作。
- 列出每项用户操作的流程、输入/结果、副作用、账户来源、超时与取消行为。
- 确定新目录与公开入口；记录所有暂时保留的跨层依赖，指定所属功能和退出条件。
- 禁止新增业务 QThread 子类、后台读取全局 current、接口/服务弹窗等模式。
- 将现有 GUI 组件、旧 Qt 绑定和资源依赖列入退出清单。迁移期旧 GUI 如需保留，使用独立旧入口；禁止同一进程混用 Qt5/Qt6 或不同 Python Qt 绑定。新入口只加载 Qt6/PySide6。

验收：功能迁移清单和遗留依赖清单完整；四层规则已能对应到现有代码位置；GUI 路线已固定，旧界面退出条件明确。

### P1：最小执行与契约基础

- 定义基础数据/错误、服务输入/结果、进度和取消契约。
- 建立统一任务记录、明确账户绑定与失效规则。
- 建立最小 GUI 执行适配器和 CLI 调用路径；同步服务在 GUI 后台执行，CLI 可直接调用。
- 建立最小 Qt6/QML 入口、Python 展示模型和 Basic Style 页面；只提供浅色/深色切换，覆盖基础输入、列表、进度和错误展示，不提前开发主题系统。
- 统一进度组件只消费任务信息；不新增复杂任务编排框架。

验收：接口/服务/runtime 导入无 Qt；CLI 不依赖 Qt；任务只终结一次；进度与错误在 GUI 主线程展示；新 GUI 可独立启动，显式使用 Basic，明暗模式下文字、输入、禁用态和进度均可辨识。

### P2：迁移一个简单功能——成绩查询

- 将成绩接口、完整查询服务、QML 成绩页/展示模型、CLI 命令贯通。
- 移出原线程中的业务代码及原页面中的 HTTP/解析/缓存逻辑。
- 保留一个临时兼容入口时，它必须单向调用新服务，不复制旧流程。

验收：GUI/CLI 得到语义一致的结果和错误；查询启动后切换账户不改变任务账户；CLI 能在无 Qt 环境使用该服务；原查询路径无重复实现。

### P3：迁移一个多阶段功能——课表同步/导出

- 用服务层编排认证、数据读取、合并、缓存和导出。
- 落实阶段、已完成量和不确定进度；覆盖失败及取消收尾。

验收：GUI/CLI 使用同一阶段和流程；GUI 页面不编排业务；中途异常不会显示成功或永久停留运行中。

### P4：迁移下载等长操作

- 将下载接口改为明确可关闭的数据流能力，进度计算留在服务。
- 明确临时文件、完成校验、取消清理与资源释放规则。
- 处理高频进度合并、关闭页面后继续任务、退出时取消与清理。

验收：不会预读完整大文件；未知大小有可用展示；取消不提前进入终态；不会遗留占用中的响应/文件；最终文件只在完成条件满足后提交。

### P5：迁移有副作用和批量操作

- 逐项迁移评教、提交等操作，先定义重复提交、超时后状态不明、部分成功和取消的语义。
- 将业务确认与交互输入留在入口，将提交/核验流程放在服务。

验收：GUI/CLI 的部分成功语义一致；错误重试不会无条件重复提交；取消后显示已完成操作及未执行部分。

### P6：扩展与清除旧架构

- 按迁移清单覆盖其他功能；每个功能完成后立即删除对应旧线程、页面业务和兼容入口。
- 最后删除不再使用的 ProcessThread/线程生命周期协议及进度控件中的线程管理逻辑。
- 清除旧 GUI 入口、Widgets/第三方 UI 组件、旧 Qt 绑定、主题资源及相关打包依赖；交付 GUI 只使用 Qt6/PySide6/QML 和官方 Basic Style。
- 对公开服务入口、CLI 用法、进度和取消限制更新文档。

验收：全部功能符合依赖规则；遗留例外清零；没有新旧两套账户/任务/业务状态来源。

异步 HTTP 或 Qt 与 asyncio 的集成仅在上述边界成立后另立计划。更换执行方式必须保持公开服务行为、进度语义及 GUI/CLI 功能一致；具体同步/异步调用适配可能调整，不承诺机械替换后一行不改。

## 13. 验证与持续约束

每个迁移功能只做与其风险匹配的验证，重点证明边界和已知故障类被处理，而不是为每个转发函数增加形式测试。

| 验证对象 | 必须证明 |
| --- | --- |
| 依赖检查 | 禁止的跨层 import、动态绕过和框架依赖能够被检查；任务契约未进入接口层 |
| 接口/服务无 UI 检查 | 导入、执行业务不需要 Qt；CLI 的依赖范围可独立安装/运行 |
| 服务流程 | 使用可控的接口替身验证完整成功、阶段失败、部分结果和取消；不必连接真实学校系统才能验证编排 |
| 生命周期 | 排队取消、运行取消、成功与取消竞态、异常、终态后迟到进度不会造成重复终结或状态倒退 |
| 账户绑定 | 切换账户、删除账户、旧结果晚到、旧缓存提交不能影响新账户或重新创建的账户 |
| GUI 适配 | Qt 控件只在主线程更新；页面销毁后订阅失效；保留任务仍有管理者 |
| QML 与样式 | QML 不访问校园接口或存储，不编排业务；展示模型在主线程更新；新 GUI 只有 PySide6 和官方 Basic，无第三方 UI 依赖；浅色/深色切换可用且不存在额外外观选项 |
| 长操作 | 流式处理、超时、取消清理、高频进度和应用退出有明确结果 |
| 真实协议回归 | 迁移后功能在必要的实际场景中仍可用；不将真实账户凭据放入测试或日志 |

静态检查作为 CI 门槛。遗留代码可以暂时登记到精确模块/文件的例外清单，但不得对整个 app 或接口/服务目录整体豁免；每项例外必须有移除条件。

## 14. 单个功能完成的定义

一个功能只有同时满足以下条件，才算迁移完成：

- 功能接口不涉及 progress、Qt、CLI 或 TaskContext。
- 完整业务流程只有一份，位于服务层。
- GUI 与 CLI 调用同一公开服务入口，使用同样的结果/错误/进度契约。
- 服务不直接访问 HTTP/ORM，不启动线程，不操作控件或终端。
- 账户、会话、缓存和写入归属明确，运行中不依赖全局 current。
- 任务状态由统一执行机制管理；取消、失败、部分成功和资源清理已定义。
- GUI 已迁移到 QML/官方 Basic；只提供浅色/深色外观，旧控件与相关依赖已退出该功能路径。
- 相关验证通过，旧路径与该功能的临时兼容代码已删除。

实施顺序：P0 盘点 → P1 最小基础 → P2 成绩查询 → P3 多阶段流程 → P4 长操作 → P5 批量副作用 → P6 全面迁移及清理。
